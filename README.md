# yamc-verification

Verification of YAMC by comparing its simulation results against the gold-standard
Monte Carlo code, OpenMC.

## Setup

```bash
pip install -r requirements.txt
```

This installs the public `yamc` package, 0.24.0 or newer, from PyPI. It brings
in the matching `yamc-core` wheel. It also installs the shared `vv` package from
`packages/vv/` (editable), which provides the `vv` command. Run it from the
repository root, since the requirements name `packages/vv` by a relative path.
To verify yamc changes that are not released yet, build the core into the same
environment instead (see [Using the latest yamc](#using-the-latest-yamc)).

## Core Validation Before a Release

Run this locally before releasing yamc or yamc-core (it is not run in CI). Build the core
checkout you intend to release into this environment, then compare Fe54, Fe56
and Fe57 with fresh OpenMC results in four modes: neutron transport, coupled
transport, D1S decay photons and material transmutation. It does not use
committed comparison results or a published yamc wheel in place of the selected
source.

Core's own regression values are generated by yamc and tightly checked there.
The OpenMC reference models and like-for-like comparison live here, rather than
determining the results core's tests require. To run them locally after building
the desired core into this environment:

```bash
python -m yamc_verify.core_validation --core-dir ../core
```

`OPENMC_CROSS_SECTIONS` can select an existing ENDF/B-VIII.1 HDF5 library.
Otherwise the harness streams the official library archive and caches only the
selected nuclides, photons and reachable depletion daughters. It uses core's
Arrow fixtures; run core's `scripts/fetch_test_fixtures.py` first. The generator
alone is available as `python -m yamc_verify.core_references --core-dir ../core`.

The comparison retains the former core validation conventions: 5% or four-sigma
scalar bands (10% for heating and photoelectric), spectral chi-square checks,
and 0.5% depletion inventories above the stated density floor. Photon heating
uses OpenMC LED with electron/positron deposition included; other photon scores
and spectra use TTB. D1S spectrum shape is gated at the peak-flux step; the other
steps' shape checks are retained as diagnostics, not additional one-bin
statistical gates. All step totals remain required checks.

Only the OpenMC depletion comparison removes MT=5 (n,X) from yamc's reactions:
OpenMC's chain does not model it. Core still regresses its full-chain solution
and checks MT=5's contribution against the evaluation independently. Daughter
cross sections are enabled in this V&V comparison, unlike the fixture-only core
regression. These differences are recorded in the report rather than treated as
yamc errors or silently added to core's expected values.

Every run writes the raw code results and `validation-results/report.json`, with
the core commit, code versions, cross-section index hash, conventions and each
required or diagnostic check. A required disagreement makes the job fail; CI
retains the artifacts for 30 days, including results from failed comparisons.

## Running the verification models

`vv plan` shows what a verification would run, and `vv run` runs it. Name the
models, the libraries and the codes, each code with an exact version or commit.
None of them has a default:

```bash
vv plan --models neutron/sphere photon/sphere --libraries endf-b8.1 \
        --codes openmc==0.16.1.dev0 yamc-cpu==0.24.0
vv run  --models neutron/sphere photon/sphere --libraries endf-b8.1 \
        --codes openmc==0.16.1.dev0 yamc-cpu==0.24.0
```

The same from Python:

```python
from yamc_verify import verification, verification_plan

print(verification_plan(models=["neutron/sphere"], libraries=["endf-b8.1"],
                        codes=["openmc==0.16.1.dev0", "yamc-cpu==0.24.0"]).format())
result = verification(models=["neutron/sphere"], libraries=["endf-b8.1"],
                      codes=["openmc==0.16.1.dev0", "yamc-cpu==0.24.0"])
assert result.ok, result.failures
```

- **Models** are task keys without their library (`neutron/sphere`,
  `secondary-photon/broomstick`, ...), or `all` for every model defined on the
  libraries. A pair that is not defined (the tokamak has no FENDL task, say) is
  listed as not run.
- **Libraries** must have their OpenMC data (a `cross_sections.xml`) under
  `YAMC_VERIFY_NUCLEAR_DATA` (default `~/nuclear_data`), in the folder
  `NUCLEAR_DATA_SUBDIRS` in `yamc_verify/tasks.py` gives for the library. A
  library kept elsewhere is named directly with
  `YAMC_VERIFY_NUCLEAR_DATA_<LIBRARY>`, for example
  `YAMC_VERIFY_NUCLEAR_DATA_ENDF_B8_1=/data/endfb-viii.1-hdf5`. The transmutation
  and decay-photon OpenMC runs use the depletion chain from an installed
  `openmc_data`, or the file `YAMC_VERIFY_OPENMC_CHAIN` names.
- **Codes** are `openmc==<version>`, `yamc-cpu==<version>`,
  `yamc-gpu==<version>`, `yamc-cpu@<commit>` or `yamc-gpu@<commit>`. Each code
  version runs in its own environment (see
  [One environment per code version](#one-environment-per-code-version)), built
  the first time it is needed and reused after that; the CPU and GPU runs of one
  yamc version share one. Two yamc builds can be compared in one call.

An unknown or missing model, library or code stops it before anything runs,
with a list of what is available.

`vv plan` builds nothing and runs nothing. It lists each code and whether its
environment is ready, then every model, library and code with how many items
already have a record that code would accept and how many are still to run, and
a rough time. The time comes from how long the earlier records took (from any
build), plus building the environments that are not ready yet:

```text
codes:
    openmc==0.16.1.dev0  environment ready
    yamc-cpu==0.24.0     environment to build (about 5 mins)

40/80 cached, 0/40 completed ETA 2.1 hrs

neutron/sphere endf-b8.1
    openmc==0.16.1.dev0 - 20/20 cached
    yamc-cpu==0.24.0 - 20/20 todo
...
estimate: about 2.2 hrs, including building 1 environment(s)
```

`vv run` builds the environments that are not ready, then runs each model,
library and code as a separate process inside that code's environment, with the
same layout as a live, in-place display. Its output goes to a log per job, named
at the end if a job fails. Records are written as described in
[Results cache](#results-cache).

Which items run is chosen by environment variables, as before:

- `YAMC_VERIFY_NUCLIDES` - comma-separated list naming the exact isotope(s) to run
  on the nuclide-based models (neutron, secondary-photon, decay-photon, transmutation),
  e.g. `Fe56`. Overrides the count cap.
- `YAMC_VERIFY_ELEMENTS` - comma-separated list naming the exact element(s) to run on
  the photon models, e.g. `Fe`. Overrides the count cap.
- `YAMC_VERIFY_NUMBER_OF_SIMULATIONS` - cap on nuclides/elements per model when no
  explicit list is given (unset or `0`: no cap). Special values:
  - `0` - no cap: run **every** discovered nuclide/element (includes radioactive ones).
  - `-1` - run every **stable** (non-radioactive) nuclide, and for the photon
    (element) models every element that has a stable isotope. Stability comes from
    the depletion chain. The already physics-restricted models (decay-photon D1S
    parents, transmutation stable seeds) are unaffected.

When OpenMC is one of the codes, the items come from its library for every code,
so yamc and OpenMC run the same items; otherwise yamc's items come from its own
data cache.

Examples:

```bash
# one isotope through one model with a yamc release and OpenMC
YAMC_VERIFY_NUCLIDES=Fe56 vv run --models neutron/sphere --libraries endf-b8.1 \
    --codes openmc==0.16.1.dev0 yamc-cpu==0.24.0

# every stable isotope/element, every endf-b8.1 model, on all three codes
YAMC_VERIFY_NUMBER_OF_SIMULATIONS=-1 vv run --models all --libraries endf-b8.1 \
    --codes openmc==0.16.1.dev0 yamc-cpu==0.24.0 yamc-gpu==0.24.0

# compare two yamc builds on the neutron sphere
vv run --models neutron/sphere --libraries endf-b8.1 \
    --codes yamc-cpu==0.24.0 yamc-cpu@86ef200e
```

`vv` finds this repository's project through `vv.toml` at its root, so it works
from any folder inside the repository.

### Running with the codes installed here

`run_models.sh` runs the tasks with whatever OpenMC and yamc are installed in the
current environment, for example a core build with uncommitted changes (see
[Using the latest yamc](#using-the-latest-yamc)). It uses the same live display,
the same item variables and `MC_BACKENDS` (a comma-separated list of
`openmc-cpu`, `yamc-cpu`, `yamc-gpu`; required, with no default). Arguments are
task keys; with none it runs every endf-b8.1 task:

```bash
MC_BACKENDS=openmc-cpu,yamc-cpu ./run_models.sh
MC_BACKENDS=openmc-cpu,yamc-cpu ./run_models.sh transmutation/material-reaction-rate/endf-b8.1
python -m yamc_verify.orchestrator neutron/sphere/endf-b8.1  # what run_models.sh calls
python -m yamc_verify.run_task neutron/sphere/endf-b8.1      # one task, no display
```

The runs only write to the on-disk cache (the database the benchmark page reads).

## Validation against measurements

Every other model compares yamc with OpenMC. The OKTAVIAN spheres
(`oktavian/sphere`) compare it with what was measured: the neutron and photon
leakage spectra of single-isotope spheres around a D-T source at Osaka
University's OKTAVIAN facility (JAERI-M 94-014), from the FENDL-2 benchmark
sublibrary.

| item | sample | vessel |
|---|---|---|
| `Al27` | 1.22 g/cm3 | 40 cm Type-II, SUS-304, 0.2 cm walls (the experimenters' own MCNP deck) |
| `Mn55` | 4.37 g/cm3 | 61 cm Type-I, SS-41, 0.5 cm walls, as the report describes it |

```bash
vv run --models oktavian/sphere --libraries endf-b8.1 --codes yamc-cpu==0.28.0
```

```python
from yamc_verify import validation

validation(models="all", libraries=["endf-b8.1"], codes=["yamc-cpu==0.28.0"])
```

`validation()` takes only validation models (`"all"` is every one of them),
and `verification()` only the models compared with OpenMC. `vv run --models
all` runs both kinds.

- **The measurement is a record** like a code's, committed under
  `tasks/oktavian/sphere/measurement/` and part of every run of the model
  (`YamcProject.fixed_records`), so it is published and archived with the run.
  It holds the measured leakage with its errors (`null` where the scanned report
  cannot be read safely or has no measurement), the experiment's source neutron
  spectrum and the tritium target's own gamma rays, so a run downloads nothing.
  `python -m yamc_verify.families.oktavian` rewrites the records from the report
  files, pinned by sha256 and downloaded once into
  `~/.cache/yamc-verification/oktavian`.
- **Leakage** is the outward surface current on the vessel's outer sphere,
  which is the vacuum boundary. It agrees with the void-shell track-length
  estimate it replaces to within 0.015% in every bin holding more than 0.1% of
  the leakage, on both spheres. The target's gammas are transported in a
  separate photon-only run and added to the photon leakage.
- **CPU only**: yamc's GPU transport has no surface or photon tallies yet.
  OpenMC does not run on these models; the measurement is their reference.
- **Not graded.** The site shows the spectra with C/E per bin, and per
  particle the integral C/E, the rms of ln(C/E), and chi2/N with the
  experimental and Monte Carlo errors in quadrature. The neutron errors are
  counting statistics only, so chi2/N is large even where C/E is close to 1.
  These comparisons stay out of the agreement bands, the deviation figures and
  the release check.

Known differences from the experiment, kept rather than tuned away: the photon
measurement gated out photons arriving later than about 65 ns after the source
pulse, while yamc runs to steady state, so slow capture gammas are included;
the Mn vessel's 5.1 cm beam hole is modelled empty, since the report does not
give the tube thickness; and the report's sample masses agree with the
modelled geometries to within 3%. The Co and Nb spheres are left out (the Co
measurement reports more leaking neutrons than its physics allows, and for Nb
every library misses by the same amount, which points at the vessel model);
the other spheres and further experiments are listed in
fusion-neutronics/example-endf-to-transport-validation#1.

## Comparing and publishing a run

A *run* is the record each item has for a set of codes: the yamc records of the
named version or commit, and the OpenMC references the run used (any build's
for neutron and transmutation, the named OpenMC version's for the photon
families). Both commands work from the stored records alone, so they need no
nuclear data and build no environment.

`vv compare` shows what changed against the newest published run, the one the
site shows. Each item is `new`, `missing`, `changed` (with its largest relative
difference and where), `rerun` (a new record with the same results) or `same`;
only the differences are listed:

```bash
vv compare --models all --libraries endf-b8.1 --codes openmc==0.16.1.dev0 yamc-cpu==0.24.0
```

`vv publish` takes the same arguments and opens a pull request publishing the
run, normally once per core release:

```bash
vv publish --models all --libraries endf-b8.1 --codes openmc==0.16.1.dev0 yamc-cpu==0.24.0
```

It refuses records from a build with uncommitted changes, and a run whose
records are exactly the newest published run's. The pull request's branch is
made from `main` on `origin` without touching your checkout or branch. It holds:

- the run's records, including any not committed yet;
- `runs/<tag>.json`, the run's manifest: its codes, models and libraries, and
  every record's path and git blob id, so the exact bytes can be read back from
  git even after a record is replaced by a rerun of the same build;
- `published.json`, the small file naming every published run, newest first.
  The site shows the first two.

The tag is `vv-<date>-<codes>`, for example
`vv-2026-11-27-openmc-0.16.1.dev0-yamc-cpu-0.24.0`. When the pull request
merges, the `Release published runs` workflow runs `vv release`: it tags the
merge commit and makes a GitHub release of that tag with the run's records
attached as `<tag>.tar.gz`. That release is the run's frozen snapshot, so old
runs can be pruned from git later.

If the run included records not committed in your checkout, `vv publish` says
so: they are on the branch, so remove them (or check out that branch) before
pulling `main` once it merges.

## Shared code (`yamc_verify/`)

All the model logic lives in the `yamc_verify/` package. Runs are driven directly
from it (there are no notebooks):

- `tasks.py`: the task registry (one `Task` per model/geometry/library: library,
  geometry, particle statistics, which codes run, whether YAMC is cached). Single
  source of truth shared by `run_task` and the orchestrator.
- `families/`: per-physics-family simulation runners, plotting, and metrics
  (`neutron`, `photon`, `secondary_photon`, `decay_photon`, `transmutation`,
  and `oktavian` for the validation against measurements),
  each exposing `run_all(task, backends, cache_dir=...)`. YAMC runs with
  `verbose=[]` and OpenMC with `verbosity=1` + `output=False`, so runs are silent.
- `run_task.py`: drives one task: dispatches `task.family` to its family module's
  `run_all` and caches the results. This is what each run process executes.
- `geometry.py`, `discovery.py`, `plotting.py`: shared geometry builders, item
  discovery, and generic spectrum-comparison plotting/metrics.
- `project.py`: `verification()` and the project the `vv` commands use:
  the models, libraries and code names, which records count as done, which
  stored records belong to each code, and how a task runs in a code's environment.
- `plan.py`: item discovery and record counting per task, for both runners.
- `orchestrator.py`: the in-place runner behind `run_models.sh`.
- `index_builder.py`: builds the site's data (`benchmarks-index.json` and the published records) from the published runs.
- `environments.py`: one Python environment per code version (`openmc==X`,
  `yamc==X`, `yamc@<commit>`); see [One environment per code version](#one-environment-per-code-version).

`cache_utils.py` (at the root) holds which records the yamc and OpenMC runs
accept and the code identity each stores.

## Shared package (`packages/vv/`)

Code that does not name a particular code lives in the `vv` package, in its own
folder with its own `pyproject.toml`, so that yani-verification-and-validation
can install it from a git tag of this repository:

```bash
pip install "vv @ git+https://github.com/fusion-neutronics/yamc-verification-and-validation@<tag>#subdirectory=packages/vv"
```

- `vv.records`: the result record format (see [Results cache](#results-cache)).
- `vv.runner`: checking a request, planning it and running it, each code in its
  own environment, through a `vv.Project` the repository supplies (here
  `yamc_verify.project.PROJECT`). A code is a name plus the recipe for its
  environment (`vv.Code`).
- `vv.progress`, `vv.dashboard`: the progress events a run emits (to the file
  named by `VV_PROGRESS`) and the live display that follows them.
- `vv.publish`: the runs: comparing the records with the published run,
  publishing them, and the release archive of each published run (see
  [Comparing and publishing a run](#comparing-and-publishing-a-run)). A project
  says which records each code has with `Project.records`, and which records
  come from no code but belong to every run of a model (a measurement) with
  `Project.fixed_records`.
- `vv.cli`: the `vv plan`, `vv run`, `vv compare`, `vv publish` and `vv release`
  commands, which find the project through the nearest `vv.toml`.

Its tests are in `packages/vv/tests/`.

Running one task in code is roughly:

```python
from yamc_verify import backends, get_task
from yamc_verify.run_task import run_task
run_task(get_task("neutron/sphere/endf-b8.1"), backends.resolve("openmc-cpu,yamc-cpu"))
```

## Adding a nuclear data library

1. Add the library's folder, relative to `YAMC_VERIFY_NUCLEAR_DATA`, to
   `NUCLEAR_DATA_SUBDIRS` in `yamc_verify/tasks.py`.
2. Register a `Task` for each model/geometry using the new library (copy an
   existing entry and change `library`/`particles`).
3. Run it (`vv run --models <model> --libraries <library> --codes ...`); the
   index builder and the benchmark database page pick up the new library
   automatically (library is a facet).

## Adding a model

1. Add a new family module under `yamc_verify/families/` (or reuse one), exposing
   a `run_all(task, backends, cache_dir=...)` like the others.
2. Register `Task`s for it in `yamc_verify/tasks.py`, and map the new
   `task.family` to the module in `yamc_verify/run_task.py`.
3. Run it with `vv run --models <model> --libraries <library> --codes ...`;
   results land in the task's cache and appear in the benchmark database page.

## Results cache

Every simulation result is a self-describing JSON record (the format is
`vv.records`; `cache_utils.py` decides which records a run accepts) at
`tasks/<model>/<...>/cache/<library>/<code>/<item>/<build_id>.json`. A record
holds the code that produced it (name, version, git commit, whether the build had
uncommitted changes, backend), the run settings and their hash, when and where it
ran and how long it took, and the results.

A record is never overwritten by another build: a new yamc commit or a new OpenMC
release writes a record next to the old one, so two builds can be compared.
`<build_id>` is `<version>+g<commit>`, with `.dirty` and a hash of the compiled
extension added for a build with uncommitted changes, and `<version>+so<hash>`
for a yamc wheel that does not report its commit (yamc-core before the release
that adds `yamc.__commit__`).

Which record a run accepts:

- **YAMC** needs a record from the installed build with matching settings, so a
  new yamc release or a rebuild re-runs it.
- **OpenMC** needs matching settings (library, particles, batches, source
  energy), and any build will do. The photon-bearing families (photon,
  secondary-photon, decay-photon) also need the installed OpenMC build while
  OpenMC runs: their references changed with openmc#4036, which corrected
  Compton shell selection and Doppler broadening. A yamc-only run never needs
  OpenMC installed.
- `YAMC_VERIFY_ACCEPT_OLD_CACHE=1` accepts the newest record with matching
  settings from any build.

The benchmark page and `python -m yamc_verify.audit` show the newest record of
each item; the audit marks YAMC results from a build other than the installed
one as stale.

To force everything to re-run, delete the cache directories:

```bash
rm -rf tasks/*/*/cache
```

## Auditing YAMC vs OpenMC agreement

To find which nuclides / simulation modes disagree with OpenMC, scan the cache:

```bash
python -m yamc_verify.audit                 # rank all mismatches
python -m yamc_verify.audit --worst 20       # only the 20 worst
python -m yamc_verify.audit --current-only    # ignore stale-build YAMC caches
```

It compares every `(task, nuclide, backend)` for which both an OpenMC and a
YAMC result are cached — reduced-χ² and flux-weighted relative difference of the
flux spectrum plus the worst reaction-rate difference (neutron), or the worst
nuclide-density difference across timesteps (transmutation) — and ranks the
disagreements. Only modes that cache **both** codes can be audited offline;
modes that cache OpenMC only are reported as "not auditable offline (run them to
compare)".

## Using the latest yamc

yamc's compiled core is built from the
[fusion-neutronics/core](https://github.com/fusion-neutronics/core) repository. To
run the verification against core changes that are not released yet, install the
core from a sibling checkout into this environment, and run it again after
pulling or changing Rust code:

```bash
pip install -e ../core/packages/yamc-core
```

The build replaces the PyPI wheel, and its new extension hash re-keys the YAMC
cache (see [Results cache](#results-cache)).

## One environment per code version

To compare builds, each code version can have its own environment, built once
under `~/.cache/yamc-verification/envs/` and reused:

```bash
python -m yamc_verify.environments ensure openmc==0.16.1.dev0 yamc==0.21.0 yamc@86ef200e
python -m yamc_verify.environments list
```

- `openmc==<version>` installs that OpenMC wheel from the wheels index named in
  `requirements.txt`. Only versions published there can be installed; asking for
  another lists the ones that are.
- `yamc==<version>` installs that `yamc-core` release from PyPI.
- `yamc@<commit>` builds `yamc-core` at that commit from a local core checkout
  (`--core-dir`, else `$YAMC_CORE_ROOT`, else `../core`), in a temporary worktree
  with its own Cargo target directory. The commit must include the build commit
  record (`yamc.__commit__`), which is how the environment is checked.

Every environment also has the verification dependencies and the other code at
its latest release, which the tools use to find nuclear data. It is checked
after it is built (the version, and for a commit that the build reports that
commit with no uncommitted changes) and only then marked ready. Environments
use the Python that runs the command, so an OpenMC wheel must exist for that
Python version.

## The benchmark database page (the site)

The deployed site is a single standalone page, `web/benchmarks.html`, served as
the root `index.html`. It shows the newest run `published.json` names (see
[Comparing and publishing a run](#comparing-and-publishing-a-run)), filterable by
simulation type / geometry / library / element / nuclide, with headline
agreement stats. Each grade that differs from the run before says what it was,
and a tile counts them. Clicking a row expands a detail view with the
interactive model geometry, the flux-spectrum comparison plot, and the
reaction-rate table. Until a run is published the page says so and shows
nothing else.

The page is a pure viewer: it holds no results data, inlines its own CSS, and
uses only relative paths. Its data is written by

```bash
python -m yamc_verify.index_builder _site
```

which writes `_site/benchmarks-index.json` and `_site/records/<blob>.json`, the
exact published bytes of every record the detail views load (read back from git
when a record has been replaced since it was published). Nothing is simulated,
and records that are not in a published run do not appear: `vv compare` shows
those.

CI (`.github/workflows/pages.yml`) installs `numpy pandas plotly` and the shared
`vv` package, copies `benchmarks.html` (as the root `index.html`), `logo.png` and
`web/models/`, runs the index builder and publishes to GitHub Pages on every
push to `main`. There is no MyST, Node, or `jupyter-book` involved.

### Serving it locally

`fetch` does not work from `file://`, so the page must be served over HTTP. Use
`serve_site.sh`, which builds the site exactly as the Pages CI does (into
`_site/`, git-ignored) and serves it, so what you see locally is what deploys:

```bash
source .venv/bin/activate
./serve_site.sh            # build + serve on http://localhost:8321/
# PORT=9000 ./serve_site.sh to pick a different port
```

It shows the runs `published.json` names in your checkout, exactly as CI does.

## Troubleshooting

### A task run fails

Check the per-job log printed at the end of the run. Common issues:

- Missing nuclear data files (correct the data path used).
- OpenMC or YAMC not installed in the virtual environment.
